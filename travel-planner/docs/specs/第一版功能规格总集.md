## 共用约定

- 页面视觉、布局和通用导航样式以[纯静态双击版 demo](../../prototype/v1/途见-双击打开.html)为基准；实际业务流程按总需求与本规格执行。S01 使用真实登录和注册验证，不沿用 demo 的静态认证行为。
- 技术栈：React + Vite 前端；Next.js 后端 API；
- 首版旅行资料保存在当前浏览器并按账户隔离，不写入 PostgreSQL，不做云端或跨设备同步。注册校验输入格式、密码和账号唯一性，不接短信/邮件验证码。
- 地点发现和美食切换浏览城市不得改写旅行档案或日程；每日行程由用户手动维护，高德路线不得重排行程。
- 费用、预算与外部参考信息分开；无站内支付、交易、退款或费用拆分。缺失信息不得补造。
- 外部数据注明来源和时效；动态数据需核实。完整旅行计划为只读聚合视图，支持导出本地 PDF 快照；不提供旅行资料备份/恢复或 AI 生成。

## S01 登录、注册与应用外壳

### Problem Statement

用户需要通过真实账号进入旅行规划网站。静态双击版 demo 只能作为页面视觉和交互样式参考，不能代替账号注册、凭据校验、会话管理或接口鉴权。若 S01 仍按任意非空输入放行，旅行数据就无法可靠地归属到对应用户。

### Solution

实现真实的注册、登录、退出和登录态保持。用户可使用邮箱或手机号注册并登录；注册时校验格式、密码及确认密码、账号唯一性，服务端将密码以安全哈希保存到 PostgreSQL。登录时由后端核验凭据并建立有期限的安全会话。注册第一版不发送邮件或短信验证码，因此只校验输入格式与数据库唯一性，不声称验证邮箱/手机号所有权。登录后进入应用外壳，刷新页面在会话有效期内仍保持登录；退出后会话失效并返回登录页。

### User Stories

1. 作为新用户，我希望使用邮箱或手机号和密码注册，这样我可以创建自己的旅行规划账户。
2. 作为注册用户，我希望系统检查邮箱/手机号格式、必填项、密码规则和确认密码，这样能及时发现输入错误。
3. 作为已有账户的用户，我希望系统拒绝重复的邮箱或手机号并清楚提示，这样账号身份保持唯一。
4. 作为已注册用户，我希望使用正确的邮箱/手机号和密码登录，这样只有有效凭据才能进入规划界面。
5. 作为输错凭据的用户，我希望登录失败时看到清楚但不泄露账户敏感信息的提示，这样我可以重试而不会暴露密码或账户状态。
6. 作为已登录用户，我希望刷新页面后在会话有效期内仍保持登录，这样正常使用时不必反复登录。
7. 作为已登录用户，我希望主动退出后会话失效并回到登录页面，这样他人不能继续使用我的登录状态。
8. 作为使用不同账户的用户，我希望应用根据登录账户隔离本地旅行数据，这样同一浏览器中的账户不会看到彼此的旅行资料。
9. 作为输入密码的用户，我希望切换密码显示状态并获得可访问的表单反馈，这样我能检查输入且可用键盘完成操作。
10. 作为已登录用户，我希望通过统一导航进入各旅行模块和完整旅行计划，这样网站结构与静态 demo 保持熟悉一致。

### Implementation Decisions

- 注册/登录标识为邮箱或手机号；注册要求两者择一作为唯一账号标识，并校验格式。
- 密码长度为 8–64 个字符；注册要求重复输入一致。服务端只存密码哈希，不记录或回传明文密码。
- 注册时检查账号唯一性；第一版不接短信或邮件验证码，因此不验证联系方式实际归属。
- 登录必须由 Next.jsAPI 校验数据库中的账户凭据；前端不能仅靠输入非空或本地标记授权。
- 登录成功建立有期限的安全会话，使用安全 Cookie；会话有效时刷新保持登录。退出需使会话失效。
- 需要登录的后端接口验证会话，不以隐藏前端页面代替授权检查。
- 账户认证记录保存于 PostgreSQL；旅行资料仍按主需求保存在本地浏览器，并按账户标识隔离。认证会话与旅行资料存储是不同数据边界。
- 应用外壳沿用静态 demo 的导航和页面风格；注册表单是必要的新流程，可在相同设计体系内扩展。

### Testing Decisions

- 验证有效注册、无效邮箱/手机号、必填项、密码长度边界、确认密码不一致及重复账号。
- 验证正确凭据能登录，错误凭据不能进入，错误提示不回显密码或敏感认证细节。
- 验证账户密码以哈希形式存储，API 不接受仅由前端状态声明的登录身份。
- 验证刷新后会话有效时仍登录、退出后会话失效、过期会话被拒绝。
- 验证需要登录的 API 在无效会话下拒绝访问。
- 使用两个账户验证同一浏览器中的本地旅行资料按账户隔离，退出或切换账户不串数据。
- 验证注册/登录表单键盘可用、错误关联到对应输入项，并在手机和桌面视口可操作。

### Out of Scope

- 邮件/短信验证码、联系方式所有权认证、第三方登录、双因素认证。
- 找回密码、密码重置、账户注销、自助修改账号标识。
- 多人协作、邀请成员、细粒度角色权限和跨设备旅行资料同步。

### Further Notes

- 前端页面视觉与通用交互样式以双击版纯静态 demo 为准；demo 中“任意非空输入进入”的静态认证行为不作为本规格依据。注册界面按同一设计风格扩展。
- 技术栈：React + Vite 前端；Next.js 提供后端 API；PostgreSQL 存储账户认证记录。
- 本规格是其他模块的公共入口；S02–S09 依赖已验证的登录会话。S02 的旅行资料仍保存在当前浏览器，按账户隔离。
- 页面行为、真实认证和 API 鉴权都需独立验收；纯静态页面演示不能证明认证已实现。

## S02 旅行档案与本地保存

### Problem Statement

各旅行模块需要共享同一份旅行上下文，包括目的地、日期、同行者、预算和偏好。用户必须能创建并管理自己的旅行档案；缺少明确的数据归属会导致美食、行程和费用被错误地关联到不同旅行。

### Solution

提供旅行总览与档案的创建、查看、编辑、删除流程。档案包含旅行名称、一个或多个国内目的地、起止日期、同行者、总预算和出行偏好，并向其他模块提供当前旅行上下文。旅行档案保存到当前设备的当前浏览器，并按 S01 已验证的账户隔离；成功保存后刷新和重新登录同一账户仍可查看。旅行资料不上传为云端账户数据。

### User Stories

1. 作为个人旅行规划者，我希望创建一份旅行档案并填写名称、目的地和日期，这样其他模块有明确的规划对象。
2. 作为计划多城市旅行的用户，我希望为一份旅行添加多个目的地并确定顺序，这样行程覆盖范围能与实际旅程一致。
3. 作为与家人或朋友出行的用户，我希望记录同行者及其需求，这样出行准备模块能据此整理事项。
4. 作为制定预算的用户，我希望记录旅行总预算和偏好，这样预算页面能提供可比较的参考。
5. 作为已有旅行的用户，我希望重新打开档案查看和编辑旅行条件，这样计划改变时不必从头创建。
6. 作为管理多次旅行的用户，我希望看到旅行列表、当前旅行及其日期状态，这样能切换到正确的规划对象。
7. 作为不再需要某份旅行的用户，我希望删除该旅行前看到明确确认和影响说明，这样不会误删关联计划。
8. 作为删除旅行的用户，我希望关联内容随旅行一并处理并有清楚反馈，这样不会留下无法归属的行程或费用。
9. 作为尚未创建旅行的用户，我希望看到空状态和创建引导，这样能自然开始第一份规划。

### Implementation Decisions

- 旅行档案是 S03–S09 关联内容的归属根；模块间不得各自创建互相矛盾的目的地或日期。
- 支持国内多目的地旅行；目的地先后顺序属于档案信息。
- 日期、预算、同行者、偏好和未填写信息应区分显示，不得把空值补成事实。
- 删除前给出确认；删除语义覆盖关联内容，界面需明确说明影响。
- 旅行数据保存在当前设备、当前浏览器，并以 S01 返回的已验证账户标识分区；刷新和同一账户重新登录后仍可查看。
- 登录凭据和认证会话由 S01/API 管理；退出或切换账户不能让其他账户读取本地旅行数据。
- S02 旅行资料不提供备份导出、恢复导入或跨设备同步；S09 的完整旅行计划 PDF 是单独的只读快照，不得声称旅行资料已同步到云端。
- PostgreSQL 保存账户认证数据，但首版不承载旅行资料。若后续改为旅行资料后端持久化，需先修订本地保存和跨设备数据规则。
- 本规格定义共享旅行上下文与总览入口，不重新定义各子模块的业务规则。

### Testing Decisions

- 验证新建、查看、编辑、切换和删除旅行的用户可见流程及空状态。
- 验证同一档案的目的地、日期、同行者、预算在相关模块中保持一致。
- 验证多目的地及顺序编辑后，各消费和日程页面仍属于当前旅行。
- 验证删除确认、取消删除和确认后的关联内容状态。
- 验证成功保存后刷新及同一账户重新登录仍能查看档案及关联计划。
- 用两个账户验证本机资料分区；切换账户不可读到另一账户资料，退出登录不误删本地旅行数据。
- 验证缺省字段以“未填写”等状态呈现，而非虚构默认值。

### Out of Scope

- 多人实时协作、共享权限、旅行资料云端同步和跨设备恢复。
- 自动推荐目的地、自动生成行程和AI内容生成。
- 旅行资料备份、恢复导入、通用数据导出或账户迁移；S09 的旅行计划 PDF 快照按其规格提供。

### Further Notes

- 前端视觉、布局和通用导航样式以双击版纯静态 demo 为基准；本规格的业务行为以总需求和本规格为准。S01 的登录/注册按真实后端验证实现。
- 目标技术栈已确认：React + Vite 负责前端与构建；Next.js 仅提供后端 API；PostgreSQL 为正式环境数据库。该技术选择本身不增加本规格的用户可见功能。
- 依赖 S01 应用外壳；S03–S09 依赖此规格定义的旅行上下文。
- S03/S04 的浏览城市是临时搜索上下文，不应自动改写档案目的地。
- S05/S06 的日程地点必须属于当前旅行规划，费用与出行准备也必须归属到当前档案。

## S03 目的地特色发现

### Problem Statement

用户需要在规划旅行时了解目的地的自然、人文及其他特色信息，并通过地图或外部信息继续核实。浏览发现内容的城市可能与当前旅行目的地不同，因此必须避免将浏览行为意外写入旅行档案或日程。

### Solution

提供按当前浏览城市查看和筛选目的地特色内容的界面，显示类别、标题、介绍、参考信息及地图查看入口，并支持收藏。用户可切换浏览城市；城市切换仅改变本模块的查询和地图搜索上下文，不修改旅行档案目的地，也不自动添加到行程。

### User Stories

1. 作为正在规划旅行的用户，我希望浏览所选城市的目的地特色，这样我能发现适合自己的地点。
2. 作为偏好自然或人文体验的用户，我希望按特色类别筛选内容，这样能更快找到感兴趣的项目。
3. 作为考虑不同城市的用户，我希望切换当前浏览城市，这样可以独立比较其他目的地。
4. 作为切换浏览城市的用户，我希望页面内容和地图搜索范围随城市更新，这样结果不会仍指向旧城市。
5. 作为正在编辑旅行档案的用户，我希望浏览城市切换不改动旅行目的地和已有行程，这样探索信息不会破坏我的计划。
6. 作为感兴趣的用户，我希望收藏或取消收藏地点，这样能保留之后查看的候选项。
7. 作为需要导航或核实地点的用户，我希望通过地图入口查看地点，这样能确认位置与周边信息。
8. 作为信息不完整的用户，我希望看到内容来源或演示信息提示，这样能判断哪些信息需要出行前核实。
9. 作为筛选后没有结果的用户，我希望看到清晰空状态并可清除筛选，这样能继续探索。

### Implementation Decisions

- 浏览城市是页面内的发现上下文；只有用户在旅行档案中编辑时才改变旅行目的地。
- 地点收藏属于发现模块；第一版不提供从发现内容直接添加到日程的操作。
- 类别和内容范围遵循 PRD；资料不足时标注为参考或演示内容，避免承诺准确实时营业信息。
- 地图底图、地点/POI 搜索、定位及地图查看统一使用高德开放平台，并带上所选地点和当前浏览城市作为查询语境。
- 与 S04 共用城市切换原则，但两模块的筛选和结果彼此独立。

### Testing Decisions

- 验证城市切换更新内容和地图查询语境，且不修改档案目的地、行程顺序或当前行程。
- 验证类别筛选、清除筛选、收藏/取消收藏及空结果反馈。
- 验证地图入口带上所选地点信息，并可从地图流程返回发现页。
- 验证演示或不完整资料的状态有明确标记。

### Out of Scope

- 自动推荐或将地点插入每日行程。
- 实时门票库存、营业状态、预约、购买、路线规划或导航服务本身。
- 用户评论社区、内容发布和后台运营管理。

### Further Notes

- 前端视觉、布局和通用导航样式以双击版纯静态 demo 为基准；本规格的业务行为以总需求和本规格为准。S01 的登录/注册按真实后端验证实现。
- 目标技术栈已确认：React + Vite 负责前端与构建；Next.js 仅提供后端 API；PostgreSQL 为正式环境数据库。该技术选择本身不增加本规格的用户可见功能。
- 依赖 S01 和 S02。
- 地图与地点内容的来源和授权应遵循主需求文档中的高德及外部信息边界。
- S04 单独规定美食发现；不得因为同属一个城市而共享筛选状态。

## S04 城市美食发现

### Problem Statement

用户需要按用餐时段、饮食偏好和城市寻找当地菜系、特色美食及可前往的店铺。店铺资料可能随时间变化，浏览美食的城市也不能擅自改变旅行目的地或既有日程。

### Solution

提供城市美食发现页，允许切换城市，并按早餐、午餐、晚餐、夜宵、小吃等用餐时段以及清淡、不辣、少盐可选、亲子友好等饮食偏好筛选。使用高德开放平台查询店铺信息，呈现来源标识和查询/更新时间；提供高德地图搜索或查看入口。页面支持搜索和收藏，不自动改写旅行计划。

### User Stories

1. 作为旅行者，我希望按城市查看菜系、特色美食和店铺，这样能提前了解当地饮食。
2. 作为安排用餐的用户，我希望按早餐、午餐、晚餐、夜宵或小吃筛选，这样结果符合当前用餐场景。
3. 作为有饮食偏好的用户，我希望按清淡、不辣、少盐可选或亲子友好筛选，这样能缩小候选范围。
4. 作为查询其他城市的用户，我希望切换美食浏览城市，这样可以探索与当前旅行不同的城市。
5. 作为切换城市的用户，我希望只更新美食结果和地图搜索城市，不改变旅行档案和已有日程，这样查询不会意外修改计划。
6. 作为寻找具体店铺的用户，我希望搜索店名、菜品或商圈，这样能直接定位目标信息。
7. 作为需要核实店铺的用户，我希望看到信息来源及最近查询时间，这样能判断资料时效性。
8. 作为准备前往店铺的用户，我希望打开高德地图查看店铺位置或搜索结果，这样能继续核实路线和营业情况。
9. 作为想稍后决定的用户，我希望收藏或取消收藏美食候选项，这样能保存偏好。
10. 作为遇到没有匹配结果的用户，我希望看到空状态并能清除筛选，这样不必误以为页面故障。

### Implementation Decisions

- 高德开放平台提供地点/店铺查询能力；不把第三方返回内容复制保存为本地缓存或数据库。
- 展示查询来源与更新时间；营业、价格、评价等动态信息均提示需以高德或商家当前信息核实。
- 城市切换仅改变美食发现查询上下文，不改变 S02 旅行目的地或 S05 已排日程。
- 用餐时段与饮食偏好筛选可组合使用；“少盐可选”“亲子友好”等不构成店铺保证。
- 收藏是原型中的用户操作状态，保存边界沿用主需求文档和 S02，不暗示跨设备同步。
- 高德地图跳转应保留店铺名称和当前城市语境；无法准确定位时退化为关键词搜索。

### Testing Decisions

- 验证城市切换、时段筛选、偏好筛选、多条件组合、搜索和清空操作。
- 验证切换城市不会改写旅行档案或日程数据。
- 验证店铺来源及更新时间可见；动态信息有核实提示。
- 验证地图入口针对所选店铺/城市发起查询，缺少坐标时使用关键词查询。
- 验证无结果和查询失败有可理解的反馈，不显示伪造的高德实时数据。

### Out of Scope

- 预订、排队、支付、优惠券、外卖、商家联系代办。
- 高德数据本地缓存或持久化，或超出平台许可的抓取和再分发。
- 对餐厅安全、过敏原、菜品供应、价格或评价准确性的保证。
- 将美食结果自动加入 S05 每日行程。

### Further Notes

- 前端视觉、布局和通用导航样式以双击版纯静态 demo 为基准；本规格的业务行为以总需求和本规格为准。S01 的登录/注册按真实后端验证实现。
- 目标技术栈已确认：React + Vite 负责前端与构建；Next.js 仅提供后端 API；PostgreSQL 为正式环境数据库。该技术选择本身不增加本规格的用户可见功能。
- 依赖 S01、S02；城市切换原则与 S03 一致。
- 高德平台密钥、配额、授权、展示规范和可调用接口需要在接入实现时依据当前开放平台配置落实；本规格不臆造接口字段。
- S05 行程里的餐饮地点由用户手动维护，不能默认为本页收藏即已排入日程。

## S05 手动每日行程

### Problem Statement

旅行档案确定后，用户需要把每天计划去的景点、餐饮、住宿和交通安排成可读顺序。第一版要求用户自行编排行程，系统不得擅自重排或自动把发现页/美食页的候选项写入计划。

### Solution

按旅行日期展示每日行程，支持用户手动新增、编辑、删除和调整地点/事项顺序，记录地址、时间或备注，并允许锁定已确定的安排。展示每日计划及未安排内容；路线信息由 S06 处理。输入与旅行档案保持关联，计划的未填写字段明确标记。

### User Stories

1. 作为旅行规划者，我希望按旅行日期逐日查看安排，这样能掌握整个旅程的节奏。
2. 作为安排一天活动的用户，我希望手动添加景点、餐饮、住宿或交通事项，这样行程由我决定。
3. 作为需要修改计划的用户，我希望编辑名称、地址、时间和备注，这样信息变化时可及时更新。
4. 作为正在优化顺序的用户，我希望手动调整当天事项顺序，这样安排符合我的实际想法。
5. 作为确认某项计划的用户，我希望锁定该安排，这样我能识别暂不希望更改的内容。
6. 作为需要取消计划的用户，我希望删除事项前看到明确操作反馈，这样能避免误删。
7. 作为浏览目的地发现或美食的用户，我希望这些候选内容不会自动加入行程，这样浏览和正式安排保持区分。
8. 作为多目的地旅行者，我希望每日安排始终属于当前旅行和日期范围，这样跨城计划不会混淆。
9. 作为资料尚未齐全的用户，我希望缺失地址或时间显示为未填写，这样我能补全而非误信系统猜测。

### Implementation Decisions

- 用户是行程创建和排序的唯一决策者；不生成、不优化、不自动插入或自动重排事项。
- 支持类别：景点、餐饮、住宿、交通；每项可包含地点名称、地址、时间/顺序及备注，具体字段依 PRD。
- 锁定状态只表达用户确认意图；不触发外部预约或不可逆操作。
- 发现和美食模块收藏与每日行程是不同状态；加入行程需用户在本模块手动创建。
- S06 每日路线基于当前手工日程计算/展示；编辑日程后路线可重新查看，但不得擅自更改用户安排。
- 不做时间冲突检查或自动调整；不完整资料如实展示。

### Testing Decisions

- 验证按日浏览、新增、编辑、删除、顺序调整及锁定/解除锁定流程。
- 验证跨日期和多目的地安排仍归属于正确旅行与日期。
- 验证发现页/美食页收藏不会自动改变日程；用户可手动在此录入同一地点。
- 验证缺少时间、地址、备注时的呈现以及删除反馈。
- 验证路线入口与 S06 的当前日期和事项集合一致，不覆盖手工顺序。

### Out of Scope

- AI/算法自动排程、自动排序、冲突检测、时间估算和自动插入候选地点。
- 订票、酒店预订、交易和日历服务同步。
- 实时协作或多人同时编辑。

### Further Notes

- 前端视觉、布局和通用导航样式以双击版纯静态 demo 为基准；本规格的业务行为以总需求和本规格为准。S01 的登录/注册按真实后端验证实现。
- 目标技术栈已确认：React + Vite 负责前端与构建；Next.js 仅提供后端 API；PostgreSQL 为正式环境数据库。该技术选择本身不增加本规格的用户可见功能。
- 依赖 S01、S02；S06 依赖本规格提供的每日事项。
- S09 汇总本规格中的日程、地址和备注，并需要能区分未填写信息。
- 修改旅行日期时关联事项如何处理应与主需求一致，不能默默丢弃用户已录入内容。

## S06 高德每日路线

### Problem Statement

手动日程建立后，用户需要理解当天地点之间的路线顺序、距离和预计耗时，并能继续使用地图导航。路线信息由高德开放平台提供且会变化，不能被误认为已预约或自动调整行程。

### Solution

以 S05 当前选定日期的已录入地点为输入，调用高德开放平台呈现当天地点间的路线、距离与预计耗时，并提供高德地图查看/导航跳转。路线展示与用户手工安排分开；地图或路线失败时说明情况并保留原日程。

### User Stories

1. 作为规划当天行程的用户，我希望查看当天各地点之间的路线，这样能了解移动顺序。
2. 作为准备出发的用户，我希望看到地点间距离和预计耗时，这样能估算交通安排。
3. 作为用户，我希望路线只基于当前日期和已录入地点生成，这样不会混入其他日期的地点。
4. 作为手动调整安排的用户，我希望路线视图尊重我在行程中确定的地点顺序，这样路线展示不会擅自改计划。
5. 作为需要实际导航的用户，我希望跳转到高德地图查看或导航，这样能使用地图提供的后续能力。
6. 作为路线查询失败的用户，我希望看到失败原因和重试/地图搜索入口，这样能继续使用自己的日程。
7. 作为正在查看路线的用户，我希望知道距离和耗时属于动态参考，这样会在出发前重新核实。

### Implementation Decisions

- 路线数据由高德开放平台提供；以当前日程顺序和当前日期作为查询输入。
- 显示路线距离与预计耗时及来源/动态提示；不承诺实时交通精度或固定数值。
- 路线计算不写回或重排 S05 的手工行程；用户更改日程后重新查看路线。
- 路线规划、地图查看/导航出口统一使用高德开放平台；无法生成路线时保留事项清单和地点信息。
- 缺少必要地点信息时明确指出无法规划的事项，不自行编造坐标或路线。

### Testing Decisions

- 验证路线输入仅含当前日期的地点，路线顺序与 S05 手工顺序一致。
- 验证距离、耗时和地图来源提示可见，外部跳转携带对应地点信息。
- 验证修改日程后路线结果可更新，但日程顺序不被改写。
- 验证地点信息不完整、服务无结果或失败时的错误/空状态与重试路径。
- 验证在静态/离线演示条件下不会将示例路线冒充成实时高德结果。

### Out of Scope

- 自动规划或优化行程顺序、交通方式决策、实时导航引擎。
- 交通票务、打车下单、实时交通保证和路线缓存。
- 通过路线结果自动改变用户锁定或未锁定的日程。

### Further Notes

- 前端视觉、布局和通用导航样式以双击版纯静态 demo 为基准；本规格的业务行为以总需求和本规格为准。S01 的登录/注册按真实后端验证实现。
- 目标技术栈已确认：React + Vite 负责前端与构建；Next.js仅提供后端 API；PostgreSQL 为正式环境数据库。该技术选择本身不增加本规格的用户可见功能。
- 依赖 S01、S02、S05；S09 可汇总路线信息但须标明其动态参考属性。
- 高德平台可用接口、密钥、调用限制及导航跳转形式以项目实际申请和平台规范为准。
- 路线查询失败不应阻断查看或编辑手工每日行程。

## S07 购买信息与旅行费用

### Problem Statement

旅行者需要记录门票、交通、住宿等购买/支出信息，并将预算、参考金额和实际金额区分开。若界面混淆价格估算和已发生支出，用户会错误判断旅行总费用。

### Solution

提供旅行费用页面，按旅行展示费用项目，支持记录项目名称/类别、日期、数量、参考总额、实际总额、外部购买链接和备注。汇总总预算、参考费用与用户录入的实际费用，并清晰区分金额含义；不处理交易。

### User Stories

1. 作为旅行规划者，我希望记录旅行相关费用项目及类别，这样能集中查看消费安排。
2. 作为准备购买门票或交通服务的用户，我希望记录购买日期、数量和参考总额，这样能预估计划支出。
3. 作为已经产生费用的用户，我希望手动记录实际总额，这样能跟踪真实花费。
4. 作为查看旅行预算的用户，我希望分别看到预算、参考费用和实际费用，这样不会把预计金额误当成已付款。
5. 作为需要购买服务的用户，我希望保存外部购买链接，这样能自行前往供应方处理交易。
6. 作为需要补充背景的用户，我希望为费用添加备注，这样能记录退改、适用人群或其他提醒。
7. 作为修改费用的用户，我希望新增、编辑和删除项目并看到汇总同步变化，这样账目能保持一致。
8. 作为未填写金额的用户，我希望空金额保持未填写状态而非被计算为零或猜测值，这样汇总真实可信。

### Implementation Decisions

- 预算、参考总额和实际总额是不同概念，界面及汇总始终分别标识。
- 实际总额由用户录入；外部链接只负责跳转，不代表已购买或已付款。
- 金额合计仅汇总有效的用户数据；缺失金额与零金额分别处理。
- 费用项目归属于 S02 当前旅行；关联删除行为遵循旅行档案删除确认规则。
- 本模块仅作计划和记账，不调用支付，不建立交易状态。

### Testing Decisions

- 验证费用项目新增、编辑、删除及类别/日期/数量/备注展示。
- 验证预算、参考总额、实际总额分别展示，修改任一金额时只影响对应汇总。
- 验证空值、零值和多个项目求和的行为，避免金额单位或小数处理错误。
- 验证外部链接能打开对应目标并清晰表明离开本站；不将跳转视为交易完成。
- 验证不同旅行间费用隔离，切换旅行后显示相应账目。

### Out of Scope

- 站内购买、支付、退款、收款、转账或订单状态同步。
- 第一版费用拆分、AA结算或同行者之间的应收应付计算。
- 自动抓取订单、银行流水或外部平台消费记录。

### Further Notes

- 前端视觉、布局和通用导航样式以双击版纯静态 demo 为基准；本规格的业务行为以总需求和本规格为准。S01 的登录/注册按真实后端验证实现。
- 目标技术栈已确认：React + Vite 负责前端与构建；Next.js 仅提供后端 API；PostgreSQL 为正式环境数据库。该技术选择本身不增加本规格的用户可见功能。
- 依赖 S01、S02；S09 汇总本模块的预算、参考费用和实际费用。
- 外部购买信息易变，用户需在供应方核实；本模块不保证链接、价格或库存持续有效。
- 遵循已接受的“外部购买、站内不支付”决策：只提供记录和计算。

## S08 出行准备

### Problem Statement

行程临近时，用户需要根据旅行和同行者整理待办、预约事项、住宿、紧急联系人及其他出行需求。若准备事项脱离旅行档案，最终旅行计划就会遗漏关键信息。

### Solution

提供旅行准备页面，按当前旅行管理同行者需求、用户自定义出行清单、预约/确认事项、住宿信息和紧急联系人，并可记录天气查询入口或备注。用户可新增、编辑、勾选和删除清单项；不提供后台提醒或实时天气服务。

### User Stories

1. 作为即将出行的用户，我希望查看按当前旅行整理的准备事项，这样能知道出发前还需要做什么。
2. 作为与同行者出游的用户，我希望记录同行者需求，这样准备清单能照顾到实际情况。
3. 作为整理行李的用户，我希望新增、编辑、勾选和删除清单项目，这样清单能随准备进度更新。
4. 作为需要确认服务的用户，我希望记录预约或待确认事项，这样能集中跟进出行前的安排。
5. 作为已经安排住宿的用户，我希望记录住宿名称、地址或备注，这样出行时能快速查看。
6. 作为重视应急联系的用户，我希望记录紧急联系人信息，这样同行者能在需要时查阅。
7. 作为关注天气的用户，我希望打开外部天气查询入口并记录备注，这样能在出发前核实天气。
8. 作为准备信息不完整的用户，我希望缺少的住宿、预约或联系人字段明确显示未填写，这样不会误以为已安排。
9. 作为管理多次旅行的用户，我希望每份清单和准备信息归属正确的旅行，这样不同旅程不会混淆。

### Implementation Decisions

- 清单、住宿、预约事项、联系人和同行者需求均关联 S02 当前旅行。
- 清单勾选状态由用户控制；不自动推断准备完成。
- 天气以外部查询入口/参考信息为限；无实时天气数据时不展示虚构预报。
- 住宿及预约内容由用户记录；不表示本站已完成预订或确认。
- 个人联系信息按用户输入展示；原型不提供真实账户云同步或敏感信息保护承诺。

### Testing Decisions

- 验证清单新增、编辑、勾选、取消勾选和删除流程。
- 验证准备信息按当前旅行隔离，切换旅行后不串项。
- 验证预约、住宿、联系人及同行者需求的展示和未填写状态。
- 验证天气入口跳转行为；未接入实时服务时无假数据。
- 验证 S09 汇总所需的准备字段能被读取，缺失信息保留缺失状态。

### Out of Scope

- 推送、短信、邮件、日历提醒或后台定时任务。
- 实时天气预报、天气警报或自动行程调整。
- 住宿/票务预订、支付及供应商确认。
- 在线紧急呼叫或联系人自动通知。

### Further Notes

- 前端视觉、布局和通用导航样式以双击版纯静态 demo 为基准；本规格的业务行为以总需求和本规格为准。S01 的登录/注册按真实后端验证实现。
- 目标技术栈已确认：React + Vite 负责前端与构建；Next.js仅提供后端 API；PostgreSQL 为正式环境数据库。该技术选择本身不增加本规格的用户可见功能。
- 依赖 S01、S02；S09 汇总本模块选定的准备信息。
- 个人开发者原型中的联系信息属于用户输入内容；展示范围应仅限相关旅行页面。
- 主需求文档若明确出行准备字段的具体清单，以主文档为准。

## S09 完整旅行计划汇总

### Problem Statement

旅行信息分散在档案、目的地、美食、每日行程、费用和出行准备模块中。用户需要在出发前从一个页面查看完整旅行计划，并迅速发现仍未填写或需要核实的事项；汇总不能制造原始模块中不存在的信息。

### Solution

提供按当前旅行聚合的完整旅行计划页面，展示旅行条件和目的地、按日期排列的日程及地址/备注、路线参考、预算/参考费用/实际费用，以及预约、住宿、紧急联系人、同行者需求和准备清单状态。页面反映源模块最新内容，对缺失信息明确标注；用户可将当前汇总导出为中文可读的多页 PDF 快照，不提供 AI 生成。

### User Stories

1. 作为准备出发的旅行者，我希望在一个页面查看当前旅行的完整计划，这样不必逐个打开模块拼凑信息。
2. 作为多目的地旅行者，我希望看到旅行目的地、日期和同行者条件，这样能快速核对计划范围。
3. 作为查看每日安排的用户，我希望按日期看到事项顺序、地点地址和备注，这样能直接理解每天计划。
4. 作为查看路线的用户，我希望看到可用的每日路线参考及其动态属性，这样能把路线信息与手工安排区分开。
5. 作为控制旅行开支的用户，我希望分别看到预算、参考费用和实际费用，这样能正确判断支出状态。
6. 作为临近出行的用户，我希望看到预约、住宿、联系人、同行者需求和清单进度，这样能检查准备情况。
7. 作为发现缺漏的用户，我希望缺少地址、时间、预订或金额的部分明确标记，这样能补充必要信息。
8. 作为刚编辑完行程的用户，我希望汇总页反映源模块最新数据，这样无需手动重复维护第二份计划。
9. 作为使用静态演示的用户，我希望示例和未核实内容有标识，这样不会把原型内容误认为真实旅行资料。
10. 作为需要离线查看计划的用户，我希望下载完整旅行计划的 PDF 快照，这样可以在设备上留存和查看。

### Implementation Decisions

- 本页是 S02–S08 数据的只读聚合视图；源模块是对应信息的维护入口。
- 同一信息不得在汇总页产生独立副本；更新后以源模块最新值呈现。
- 预算、参考费用、实际费用分别显示；路线、店铺和外部参考数据标注来源/时效。
- 未填写字段、无路线结果、待确认事项显式呈现；不生成或推断事实。
- 汇总范围按 PRD：旅行条件、日程、地址/备注、费用、预约/住宿/紧急联系人、同行者需求和准备清单。
- 页面提供“导出 PDF”操作；用户主动触发后生成当前旅行的 PDF 快照并下载到本机。导出时读取汇总页最新数据，文件不上传或保存到服务端，之后的资料修改不自动更新已下载文件。
- PDF 中文字和多页分页应可读；敏感字段遵循页面遮盖规则。导出失败时说明失败且不得提示成功。
- PDF 不嵌入高德地图底图、POI 查询结果快照或高德实时路线/距离/时长；相关动态地图信息引导用户前往高德查看。PDF 是汇总快照，不是旅行资料备份或恢复文件。
- 不提供其他格式/图片导出、分享链接、独立打印版或 AI 自动生成计划。

### Testing Decisions

- 创建覆盖各源模块数据的旅行，验证汇总字段完整且与各模块一致。
- 修改档案、日程、费用或准备信息后重新查看，验证页面反映最新值且无重复/过期副本。
- 验证多日期、多目的地顺序，地址、备注和路线归属正确。
- 验证三类金额保持区分，缺失值和待确认状态不会被补造。
- 验证空旅行和部分信息旅行的汇总可读、缺漏提示明确。
- 验证演示信息标记保持可见，不把样例内容呈现为已验证的真实预订或实时数据。
- 验证下载的 PDF 与导出时汇总内容一致，中文可读且长计划正确分页；更新源数据后再次导出得到最新快照。
- 验证敏感字段保持遮盖，高德地图/POI/动态路线数据不被嵌入 PDF；导出失败时有明确反馈且不误报成功。

### Out of Scope

- 图片或其他格式导出、分享链接、独立打印版和完整旅行资料备份/恢复。
- AI自动补全、总结或重排旅行计划。
- 在汇总页直接编辑源模块字段或提供独立数据副本。
- 实时同步外部店铺、路线、预订或支付状态。

### Further Notes

- 前端视觉、布局和通用导航样式以双击版纯静态 demo 为基准；本规格的业务行为以总需求和本规格为准。S01 的登录/注册按真实后端验证实现。
- 目标技术栈已确认：React + Vite 负责前端与构建；Next.js 仅提供后端 API；PostgreSQL 为正式环境数据库。该技术选择本身不增加本规格的用户可见功能。
- 依赖 S02–S08 的数据契约与空值语义；S01 提供导航入口。
- 若源模块暂不支持某类信息，汇总页应标注未支持/未填写，不用静态样例掩饰缺口。
- 该规格对应需求中新增的“最后完整旅行计划”能力，是第一版用户可完成规划闭环的重要入口。
